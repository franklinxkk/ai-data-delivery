# 两批材料的建图练习

这里全部是合成材料，不是真实监管政策。使用新建项目，从页面正常上传 `transport.sql`、`transport-v1.txt`，检查结构和原文，再请宿主提出候选。语义判断不能由 DDL 外键代替。

第一批核对企业、营运车辆、登记车辆、监管关系、维护职责、异常车辆指标、在营企业及销售/财务两种收入。将监管关系的谓词保存为误写草稿后，依据第 7 行改回“监管”，确认并重新打开检查。加入 `conflict-b.txt`，比较与来源 A 的差异；本练习指定保留 A，拒绝 B 并记录理由。发布第一份语义包。

第二批将 `transport-v2.txt` 的内容更新到原 `transport-v1.txt` 来源，而非新建第二个来源。先接受“运营车辆”别名，暂缓职责变化；验证含职责的范围不能确认发布，仅车辆知识可单独发布。随后对照新条款，明确采纳保存维护记录要求，分别说明未变定义为何保留，再发布第二份包。旧包不改。

把两份包及读取器交给未参与构建的调用方，让其说明维护职责、监管关系、别名、指标口径及版本差异，查询无领域“收入”和材料未给出的补贴标准。不能以定义已确认声称已经可以执行 SQL。

`observations.csv` 仅供按定义核算：同一统计日，E01 的 V01 有两条有效异常记录，V02 正常；E02 的 V03 有一条有效异常。用于检验“记录条数”和“车辆去重数”是否分清。

维护者可使用 `maintainer/propose_acceptance.py` 生成本固定练习的显式提案；它不是通用文本抽取器，也不会接纳候选。日常材料由宿主阅读后生成候选。依赖完整的一组建议应一并提出；若先确认了上游对象，旧基线的下游建议需要重新提出。
