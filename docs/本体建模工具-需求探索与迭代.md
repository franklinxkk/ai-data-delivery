# 本体建模工具 · 需求探索与迭代

2026-11-20 需求评审稿。基线为本地安装包 `0.3.7-preview.1`。下文的拟迭代行为和验收样例尚未发布。

## 产品选择

用户拿来一份表结构、一段业务说明，或者提出一个具体问题。工具应尽快让他看见正在建的对象和关系，能纠正一条错误解释，也能把带依据的结果交给下一个本机 Agent。只要结构草稿的用户，仍可直接导入、导出。想弄清业务的用户，从手头的问题继续，不必另建任务或填写全行业模板。

第一条完整业务链建议选“隐患整改”。它同时检验人、车、企业、线路、场地等业务对象，监管材料里的要求，以及用工单数据计算的指标。范围随业务问题展开。把一个参与方建模为对象，需要能够说明它在这项业务中的身份和关系。来源不足时保留候选和缺口。

## 一次建模在操作者眼里是什么样

以下是拟议交互。用户把 SQL 拖给宿主，说“我想知道哪家企业负责整改”。工具先给一张能点开的局部图，标出隐患记录、工单和引用的企业字段。若同一行还存了车牌和驾驶员姓名，它可以提出“这里可能同时涉及车辆和驾驶员”，并给出来源。只知道姓名时先保留候选身份。用户可以立即带走结构图，也可以继续补材料。

接下来只问能改变这张图的问题，例如“工单上的企业是被检查单位，还是实际整改单位？”用户可以在对话里回答，也能点图上的候选关系，看两端、方向和依据，直接改成“由该企业负责整改”。输入一个目前没有的对象时，就地新建；初次只需能识别的名称，挂在当前项目，业务域可后补。选择已有对象时按名称列出来源和角色，避免选中同名单位。

保存后立即展示刚改的那一段图。支持内嵌预览的宿主展示同一修订的实图或截图，并保留打开编辑器的入口；纯 CLI 返回同一位置的本地链接和简短变更说明。例如“已确认工单由整改企业负责。该工单的复核凭证仍未找到。”操作者可以在这里结束，下次由另一个 Agent 接着查。

## 建议进入下一预览的四项需求

| 优先顺序与任务 | 操作者实际经历的行为 | 正例与反例验收 |
|---|---|---|
| **1　从问题起模并随时看图**。业务人员说“看看这家企业的隐患由谁整改”。 | 已有对象时，先显示相关企业、隐患、责任方及有据的关系。从 DDL 起步且只有外键时，先给结构草稿，业务责任作为候选。用户可把“一家企业有多辆车”改成给定材料所支持的关系，或保留未知。首次有图和重要关系变化时，宿主展示实际局部图；无界面调用仍得到可复用的定位。 | 在同一项目先导入结构，再补充业务材料。操作者能从图上找到此次新增的边、两端和依据。画布已全屏、正在编辑别的对象时，保留未提交输入，提供“查看刚改的关系”。从同一修订重开仍可查看。只有 `enterprise_id` 时不得自动确认产权或整改责任。 |
| **2　找出该对读的材料，把分歧说清**。数据人员补入一份地方实施材料。 | 用明确引用、共同业务对象或同一要求的表述给出少量候选，并说明为什么找到。地域、对象范围、有效时间同时可见。并排展示原文和位置，分别指出两边对谁、在什么条件下、要求做什么、须有什么凭证。允许选择并存、细化、新增义务、确有冲突或暂缓。确认的是本次判断，保留各自原文和修订。 | 用同主题跨范围、有显式引用的材料，加一份同地域但无关的材料。相关原文应当能在无需输入来源 ID 的情况下被找到。仅凭文名、相同关键词或行政层级不得认定“加码”。地域或时间不相交可并存。只改一份来源时，列出依赖这段原文的判断和指标以供复核，旧包仍能按原版本读取。 |
| **3　把义务、指标、数据证据连成可检查的路径**。用户问“闭环率能证明已经复核了吗”。 | 图上可从条款到具体要求、从要求到可参考的指标、再到字段与记录所需的凭证。点一段即见对应依据。多个实现可共用“闭环率”名称，但分别显示粒度、范围及数据来源。没有依据的语义边显示“待核对”，未采集实际记录时说明还缺什么。 | 合成口径按隐患编号计数。同一隐患有两张工单时，按工单加和的实现要暴露重复风险。只有关闭时间时，可以解释系统关闭口径；问“某隐患已复核吗”应提示缺少该隐患的复核记录。加入一条关联到另一隐患的凭证，原缺口仍在。补齐同一隐患的映射后，只更新可取证路径；没有观测数据时仍保留事实核验缺口。 |
| **4　人和 Agent 消费同一张局部图**。宿主在对话里补一条关系，另一 Agent 离线接手。 | 普通材料任务可以临时按业务对象或当前问题选范围，返回相关项、必需依赖、已省略的数量和继续查找的入口。用户无需先保存一个问题。不确定对应哪个“企业”时展示带来源和角色的候选。局部图、CLI 回执和离线包用同一资产 ID、修订和依据定位。 | 在上述 400 项夹具中选中一个表，任务只返回它与实际依赖，并说明其他内容可检索。找不到对象时主动提示选择，不退回到默默发送全库。离线 Agent 能给出正确路径，或指出断在哪一段；仅返回正确终点或有效 JSON 不算完成。重复导入、拒绝候选和旧包读回沿用现有行为。 |

完整业务链需要“确认”的是有争议的含义、身份或适用范围。有明确依据的内容允许按组核对。纯结构导出不强加这四个步骤。工具负责版本、一致性和原文定位。宿主负责理解自然语言，业务负责人对范围和适用口径作出判断。

## 首个验收样例

采用以下**虚构材料**，仅用来试工具。通用说明 A 要求企业登记整改结果。适用于甲地区的材料 B 明确引用 A，另要求复核凭证关联同一隐患。另一份同属甲地区的材料 C 讲车辆保养。系统有隐患、整改工单、结案时间，暂缺可与隐患关联的复核凭证。

1. **查要求。** 用户问“甲地区多要求留什么”。从 B 定位到 A，对读后得到“同一隐患的复核凭证”，能点回两段原文。C 可以手选查看，不能因地名相同成为新增要求的依据。另一地区或 B 生效前的情况分别处理，适用时间缺失就显示未知。
2. **查责任。** 被检查企业、整改责任单位、复核人分别建模。两种职责可以由同一主体承担，只有代号、同名或一条外键时不合并身份。选择“暂不确定”后，下一轮继续使用原候选。
3. **查指标和个案。** 隐患 H1 有两张已关闭工单，只有 H2 有成功复核记录。能解释 H1 的关闭记录、指出 H1 的凭证缺口，不能把 H2 的记录补给 H1，也不能从汇总百分比推出 H1 已复核。
4. **查变化。** B 发布新版本，凭证要求变化。显示哪些定义直接引用旧条文、哪些指标间接受影响、哪些关系仍有 A 单独支持。业务人员可核对后采用或保留有理由的历史范围。重新打开先前导出的包，仍可读到原结论及其当时依据。

真正有区分度的试用，是让未参加建模的人用交付包完成这四个问题，用业务人员事先确定的预期核对对象、关系方向、适用范围、缺口和出处。另用同一批材料让宿主直接回答，比较错误、追问、人工修正和第二次交接时的表现。首轮记录每条任务的完成时间和误判，不以样本量或一次演示推定行业普适性。

## 保留为探索的问题

- **自动找跨范围材料。** 首先试显式引用、可核对的业务同义词和已确认关系。比较“相关材料被遗漏”和“无关材料占据首屏”两种失败，再判断向量检索的增益。手动指定已登记材料始终可用。
- **2D 与 3D。** 首先让 2D 全屏内能搜索、定位最近变化、分批展开，并让长布局可取消。复用原密集图夹具，区分全图完成耗时与用户多久能继续操作。若用户在陌生网络里寻找跨域路径仍频繁漏边，再用相同模型、问题和屏幕比较 3D 的准确率、用时及截图交接效果。
- **行业覆盖。** 先在交通跑通一个多对象、多来源、可反向追溯的全过程，再以独立业务材料迁移一次。候选为高校的学生与多项目注册、制造的批次与返检。下一行业的业务负责人需独立给出期望和例外，才能评价口径正确性。

首轮试用成立的信号，是接手人能在无原建模者陪同的情况下说明“这里用了哪条规则、适用于谁、还缺哪份证据”，以及原建模者只需更正那一处。试用通过后再决定外部格式扩展和更大范围的行业声明。

继续跟踪社区时，每个新案例只回答三件事：用户当时要完成什么、什么输入导致了错判、我们的安装包遇到同样输入会怎样。能本地复现且影响上述任务的，补充正例和反例；只出现于别的产品、尚未验证与本工具相关的，留作研究线索。论文、会议摘录和合成行业材料放在维护侧，使用者下载的工具只携带执行所需内容。
