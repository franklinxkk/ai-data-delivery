# M1/M2 implementation contract

Baseline: 414ab47. User approved M1/M2 on 2026-11-09 and explicitly removed pre-1.0 backward-compatibility requirements. This is an internal implementation contract, not a user-maintained input format.

Canonical semantic assets live in `document.model.semantic = {schema_version: "1.0", assets: [...]}`. No parallel graph truth. Existing numeric tools remain available separately; no old-project migration is required.

An asset has `id, kind, name, definition, domain, scope, aliases: [], status: draft|confirmed|needs_review|retired, properties: {}, refs: [], evidence: [], effective_from, effective_to` (missing dates mean unspecified). Kinds: entity, term, attribute, relation, metric, rule, dataset, field, mapping. IDs are immutable and project-wide unique. A relation/mapping also has `from, to, predicate, relation_type`; core relation types: business, is_a, denotes, has_attribute, measures, applies_to, depends_on, maps_to, physical_fk. Physical FK keys live in properties.from_fields / to_fields; business predicate is not inferred from FK. `refs` is the list of explicit required dependencies. Merge redirects live in `semantic.redirects`.

Evidence: `{source_id, revision: integer, extraction_id, fragment_id, quote}`. Bind the returned extraction identity; a fragment appearing in several extractions must not be guessed. Manual assertions use `{type:"manual", quote, actor, created}`. Evidence is attached per asset/assertion, not merely to the project. An attribute or relation can be a separate asset to preserve its own evidence.

### Required properties when confirming / 确认时必需的属性

Use these exact keys inside `properties`; descriptive synonyms are not aliases. Draft proposals may omit them, but confirmation reports missing fields and leaves the group unchanged. Common required confirmation fields are nonempty `definition`, `domain`, `scope` and valid evidence.

| Kind / 类型 | Exact keys / 准确字段名 | Meaning / 含义 |
|---|---|---|
| `metric` | `unit`, `grain`, `inclusions`, `exclusions`, `time_scope` | Unit, distinct/counting grain, included records, excluded records, data window or cutoff / 单位、去重或统计粒度、包含项、排除项、数据窗口或取数截点 |
| `rule` | `condition`, `requirement` | When applicable; required or prohibited behavior / 成立前提；要求或禁止行为。Use singular keys, not `conditions` or `requirements`. |
| `attribute`, `field` | `value_type` | Value type / 值类型 |

For example: `"properties": {"condition": "Greenhouse H1, active plant with a known latest moisture value", "requirement": "Below 30 percent requires human review; missing readings remain unknown and do not authorize watering"}`. Other kinds have no additional required property keys; relation endpoint/type checks still apply. This example is fictional, not a default business policy.

`effective_from/effective_to` describe a definition's validity interval. Scenario/reader `as_of` asks whether definitions (including dependencies) apply on that date; absent validity bounds remain unknown. It is **not** the data cutoff. Put a data cutoff/latest-record rule in `metric.properties.time_scope` and its reviewed rule/evidence. Leave `as_of` unspecified when no definition-applicability date was requested; never invent validity dates to clear a check. / 定义有效期与取数时间分开保存；不得为了通过检查虚构有效期。

Business scope from introductions, section qualifiers and exceptions must be represented in the applicable asset `scope` and supported by its evidence. Shared scope can be an evidence-linked rule required through `refs`; do not substitute a draft/simulation label for business restrictions. Preserve negative requirements in the rule's normative fields. `properties.knowledge_gaps` is an optional unique list of nonempty strings describing explicitly unknown business information, not inferred defaults. These gaps are returned by the consumer context endpoint; their presence does not mean the stored definition is structurally invalid or authorize a business answer.

Knowledge state lives in `document.knowledge = {sources:[], batches:[], groups:[], separations:[]}`. Source `{id,name,format,domain,scope,current_revision,revisions:[]}`; source revision `{revision,sha256,attachment_id,created,parsed,current_extraction,extractions:[{id,parsed,created}]}`. Re-extracting unchanged bytes with different options preserves the content revision and adds an extraction; existing evidence keeps its original extraction. Parser returns `{format,status:complete|partial|failed|needs_conversion,fragments:[{id,location,text}],warnings:[],structure:{...}}`. Text fragments have line/paragraph locations, DDL fragments statement locations, Office cell/paragraph and PDF page locations. Parser does not mutate project or call LLM/network. Source import returns deterministic DDL/structured suggestions via backend and can create host jobs for unstructured semantics.

Batch `{id,status:pending|running|review|partial|failed|cancelled,sources:[{source_id,revision,extraction_id}],base_revision,created}`. Group `{id,batch_id,summary,status:pending|accepted|rejected|deferred|stale,base_revision,candidates:[],reason}`. Candidate `{id,op:upsert|retire,target_id,asset,evidence,reason,target_fingerprint,dependency_fingerprints}`; upsert asset is a full proposed asset. Existing targets and dependencies compare fingerprints captured at submission. Put newly introduced dependencies and their consumers in the same group, or propose consumers after their dependencies are confirmed. For a new candidate asset missing ID, backend allocates one. Host supplies IDs to refer between candidates. Group application is atomic. Reject/defer persists; same proposal replay preserves dispositions. Identity merge is an explicit workbench action, not a host candidate operation.

Authoring dependencies include `refs`, relation `from/to`, and optional `properties.execution.refs/data_refs`. These participate in deletion guards, merge rewrites, candidate staleness and execution invalidation. Semantic-only publication omits optional execution declarations; explicit semantic dependencies still close normally. Same-name identity decisions apply to the actual closed publication scope; draft packages retain unresolved identity issues without changing workspace definitions.

All mutation requests carry `revision` and `operation_id` (UUID generated client-side; reuse on network retry). Query an existing operation before checking revision. Different payload under same operation_id is rejected. Response `{revision,result}`. Validation failures use HTTP 400, stale revision 409, no partial graph writes. UI preserves form state on errors.

HTTP API (root agent implements service/routes):
- GET `/api/knowledge/state`: `{revision,document,layout,history,assets,sources,batches,groups,problems,snapshots}`; source parsed fragments included.
- POST `/api/knowledge/import`: `{filename,content_base64}` or `{filename,text}`, optional `source_id,distinct_source,domain,options` (CSV/XLSX sheet/header/range). Returns source_id,batch_id,parse result; default incremental.
- POST `/api/knowledge/task`: `{batch_id,action:prepare|cancel|resume}`. prepare returns selected material fragments + current assets + proposal instructions, marks running. Cancel does not admit late results.
- POST `/api/knowledge/propose`: `{batch_id,groups:[{id?,summary,candidates:[...]}],complete:true|false}`. Host CLI invokes same service.
- POST `/api/knowledge/review`: `{group_id,action:accept|reject|defer,reason,assets?:[edited asset...]}`. Accept confirms after validation. Reject/defer reasons persisted.
- POST `/api/knowledge/edit`: `{asset,confirm:boolean}`. Manual new/changed content can add manual evidence through UI; source evidence is preserved unless explicitly changed. Draft does not require all semantic fields.
- POST `/api/knowledge/merge`: `{survivor_id,merged_id,resolved_asset,reason}`. Retains redirect, rewrites references atomically; unresolved differing definitions need explicit resolved_asset.
- POST `/api/knowledge/separate`: `{left_id,right_id,reason}`.
- POST `/api/knowledge/retire`: `{asset_id,reason}`; delete only unreferenced unpublished draft via action:delete.
- POST `/api/knowledge/review-source`: `{asset_id,action:retain|adopt,reason,asset?}`; explicit source change review, preserve old evidence if retained.
- POST `/api/knowledge/undo`: `{target_revision}` only safely reversible semantic operation, creates new revision.
- POST `/api/knowledge/publish`: `{asset_ids:[] (empty means all business semantics),draft:false,include_execution:false}`. Uses common reader/export library. Returns snapshot_id, filename, download_url and manifest with actual scope/issues; persisted immutable bytes on success.
- GET `/api/knowledge/download/<snapshot_id>` returns ZIP. Direct browser downloads accept a short-lived server-session HttpOnly, SameSite=Strict cookie scoped only to that path; other APIs still require the session header and origin checks. GET `/api/knowledge/source/<attachment_id>` returns original attachment after session guard.
- POST `/api/layout` existing persistence, keys `semantic:<view>:<asset_id>`; layout changes do not change semantic revision.

Standalone package contract (consumer agent owns `workbench/semantic_package.py`, `scripts/semantic_read.py`): ZIP or extracted directory containing model.json (schema_version and assets), sources.json (selected source revisions/fragments), manifest.json (format_version, snapshot_id, source_revision, scope, draft, sha256 files), README.md and human-review.html. No private project SQLite or original attachments. `build_package(assets,sources,*,project_id,revision,asset_ids=None,draft=False,include_execution=False,snapshot_id=None) -> (bytes,manifest)`; may raise ValueError on invalid dependencies/status/evidence. `package_preview(...)` optional. Reader API `read_package(path)`, `search`, `get`, `neighbors`, `sources`, `export`, `verify` should all use same schema. Include redirect information if present; agree any extra keyword with root. CLI requires explicit package path and emits machine-readable JSON, snapshot and actual scope, with structured errors and nonzero exit on corrupt/unsupported; ambiguity is returned explicitly. No LLM or original workspace access needed.

Delivery main flow: inputs -> candidates -> human review -> canonical assets -> graph edits -> fixed package -> independent read. Text does not magically become confirmed semantics: host Agent returns evidence-linked proposals, or operator manually creates. Native structured deterministic extraction only reports what is explicit. Source import/parse must visibly work without a host; host preparation has a copyable instruction, no raw JSON required from user.
