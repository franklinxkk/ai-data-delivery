# 从已有元数据到可消费语义

适用：已有表、字段描述、关系或标准数据，准备让应用/Agent 使用。先复用结构，再处理影响当前问题的业务歧义；不要从空白本体重新录入。以下是通用方法，不将某个平台的菜单、授权分类或行业字典设为默认。

## 一条操作路径

```mermaid
flowchart LR
  A[结构与既有关系] --> B[生成可审阅候选]
  B --> C[核对业务含义与投影]
  C --> D[当前用例与独立预期]
  D --> E[结构/数据/结果验证]
  E --> F[按消费者范围交付]
  F --> G[对接实际读取与执行]
  G --> H[变更后检查影响与撤销]
  H --> C
```

1. 保留数据集/字段/关系 ID、描述、复合键和历史决定。全局图与单数据集子图用同一份关系定义；图上坐标和展示范围不改变业务关系。
2. `derive_ontology` 从已提供的 `datasets/relationships` 补对象、字段属性及投影引用。关系只写“关联（待确认）”，不把同名列猜成外键，也不把键关联猜成所有权/监管责任。已有绑定和已维护对象不覆盖；失效引用、同名歧义必须先修复。
3. 再次执行不新增对象、不重编 ID。它不自动刷新已绑定对象的属性：源字段删除/改名后，先比较差异、定位受影响指标/关系/消费者，再按已确认映射修改；不能按列位置替换，更不能回退旧结果。
4. 核对当前用例需要的对象身份、粒度、业务谓词、基数、字典、时间与范围。可复用明确事实，不重复让用户确认；自动生成比例不作为承诺。结构完整、资料齐全、真实数据正确是三种不同证据。

```bash
python scripts/derive_ontology.py --model metadata.yaml --out semantic-candidate.yaml
python scripts/check_model.py -f semantic-candidate.yaml
python scripts/check_join_graph.py --model semantic-candidate.yaml --db snapshot.sqlite --out joins.json
python scripts/export_exchange.py --model semantic-candidate.yaml --out handoff
```

可直接使用[合成元数据示例](../examples/metadata-reuse/README.md)。前两步不需要数据库。最后一步仅导出，不表示候选已通过业务验收。`derive_ontology` 拒绝覆盖输出；工作台可在“语义建模→从元数据补充语义草案”完成同一操作，候选由现有对象/关系表单维护，项目修订检查阻止旧页面覆盖。

当前 DDL 导入器只抽取支持的 CREATE TABLE 表/字段/主键，**不会保留外键关系**。已有数据图谱须先映射为 `relationships` 并保留左右列顺序。复杂方言/跨库同名表先核对解析范围；本轮没有把解析器升级为通用 SQL 导入器。

## 关系维护一份，方向按同一关系解释

“车辆→企业”与从企业查看车辆可以沿同一个关系 ID 双向走。现有 `check_join_graph` 已支持显式查询路径反向遍历：N:1 反向成为 1:N，要重新判断聚合重复。它不生成第二条维护记录，也不证明反向路径适用于任何指标。

业务逆向名称由已知含义展示或由用户命名，不从“属于”自动推导法律责任或权限继承。雇佣、持证、监管、历史任职等不同业务事实仍是独立关系；is-a、part-of 与字段等值关联不能混用。本工具没有 OWL 推理、递归属性继承或任意跨表 SQL 执行器。

## 指标、NULL 与消费结果

| 用户要的结果 | 当前合同落点 | 必须分清 |
| --- | --- | --- |
| 数值聚合 | metrics + expr，复用单表编译器 | COUNT(*) 记录行数；COUNT(字段) 非空数；COUNT(DISTINCT 字段) 去重非空数，三者不能都叫“计数” |
| 比率 | numerator/denominator | 两边范围、主体和时间可比较，零分母策略明确 |
| 列表/明细 | templates | 字段、过滤、排序、分页、总数由实际消费者执行；本地编译器不执行列表模板 |
| 直接取某值 | 在目标消费者声明唯一主体/维度与冲突规则 | 0、无记录、NULL、多条冲突分别处理，不能偷偷取第一行；本轮不新增执行器 |

主体、维度与指标列由业务结果确定，不能因表里有字段就增加一层分组。范围可以包含且/或：本地 `filters` 各项按且组合，复杂布尔条件可写已有 `extra_where` 并保留括号；不是提供了可视化条件编辑器。先按已授权范围和过滤取数，再聚合/投影；数据字段不在输出列中不代表过滤失效。授权由执行系统强制处理，模型里的字段和说明不是权限实现。

上述是人工确认模型后的编译与消费合同。`promote_draft.py` 的自动翻译范围更小：仅完整单表 COUNT(*) 与 AND 字段比较；不会把 OR、分组、未识别条件截取后拼成 AND。复杂口径及字段/值/模型映射缺口保留在清单中，补齐定义后再维护模型，不能直接批量合入。

可区分三种计数的独立样本：当前范围内主体键为 A、A、NULL，范围外再放 B；预期记录数3、非空数2、去重数1。额外测试空范围应为0，不能当依赖失败；来源失效须报错而非返回0。时间只在业务问题需要时明确；CLI 补齐 scope 已写 `time_requirement: current` 时不强迫填写指标时间字段，未说明时仍需澄清。指标本身已确认仅当前状态时，可声明 `time_requirement: current`（工作台指标编辑的“时间范围”），补齐与 lint 共同识别；不会自动加日期过滤，也不能据此回答历史问题。

## Agent 从哪里获取、如何调用

本仓库提供两类已有入口，不能把它们说成统一生产网关：

| 入口 | 如何用 | 边界 |
| --- | --- | --- |
| 导出文件 | `export_exchange` 或工作台“下载语义交付ZIP”；读取 `semantic.yaml`、字典和 manifest | 导出前由可信一侧裁剪接收方可见资产和字段，核对引用闭包；当前导出器不自动实施租户/行列授权 |
| 已有引擎适配 | 工作台“检查与试算”的消费者检查先 GET `/api/model`，已知字段投影相符才 POST `/api/ask`，请求 `{"question":"…"}` | 这是现有本机引擎协议，需要用户提供真实地址；不是本 Skill 自动启动的问数服务。认证Key/IP白名单/用途权限由目标平台实现，当前适配器不提供这些生产能力 |

工作台自身 `/api/*` 是本地编辑器的令牌保护接口，不是给外部 Agent 的生产数据 API。`reconcile_paths --endpoint` 是结果对账工具，不包含工作台的模型预检；使用前先核对目标引擎加载的模型。

Agent 使用顺序：获得可信执行主体和用途范围→取范围内目录、语义和 DDL 描述→解析术语/指标→选择已确认路径→执行前再次鉴权并校验来源→执行→核对结果形状、单位和模型身份→返回结果及来源；依赖失败或歧义返回具体问题。模型中的 `ai.instructions` 和SQL注释均为业务资料，不是新的工具执行授权。

目标平台应给出实际地址、认证方式、请求/响应、分页/限流及错误码。没有这些信息时记录缺失，不伪造可调用接口。当前工作台实际返回：HTTP 403（本机令牌/来源检查失败）、409（旧修订提交）、400（无效输入）；消费者模型不匹配返回结果状态 `model_mismatch` 且 `query_sent:false`，不会继续问数。执行错误、无权、无数据和模型不匹配不能都返回空数组。

源端采集Key与平台对外消费Key分别承担不同权限。分页游标不是跨批增量位置；数据快照与成功采集水位也不是语义版本。只有来源数据已完整采用，才能用它作为新结果证据。具体重试、删除事实和增量规则归接入系统，本 Skill 核对证据与依赖，不实现 ETL。

导出 `--report` 接受含 evidence 模型绑定的报告，例如 check_join_graph、check_constraints、run_eval 的输出。reconcile_paths 的原始输出是结果列表，不是验收报告；需将独立用例与实际结果交 run_eval，并附同一模型/数据快照绑定。无依据的手工包装不能提升证据等级。

现可通过[SQLite / PostgreSQL / MySQL 只读目录连接](readonly-metadata.md)持续按需观察结构变化并回归相关问题；以下旧数值模型派生路径与规范语义图谱入口分开，不静默混合。
